## Условие UX-01 — сохранение изменений во время Save

**HIGH, structural; владелец qcsd-ux.** `04_domain_model.md` описывает draft → PATCH → canonical response → saved и сохранение draft при ошибке. Оно не определяет, что произойдёт с изменением, сделанным после отправки и до успешного ответа. Возврат canonical snapshot может затереть более поздний ввод или представить его сохранённым, хотя он не был частью запроса. Это допущение, разрешённое неполной спецификацией, а не наблюдённый дефект приложения.

До admission определить: во время запроса editing блокируется либо последующие изменения остаются в draft как dirty; успешный ответ применим только к отправленному snapshot. Запланировать browser тест с задержанным ответом, проверяющий сохранение/невозможность изменения и достоверный status. Проверить отдельно две вкладки: для разных dirty keys оба изменения переживают reload, для одинакового key действует выбранное в ADR-001 last committed write wins, после reload видно итоговое значение. Это проверка уже выбранной модели, не требование version lock или нового сервиса. Scope: `01_requirements.md`, `04_domain_model.md`, `03_adr/001-patch-existing-branding.md` внутри host manifest.

## Проверка пути и ограничений

- Dashboard → owned project → branding и назад без ручного URL предусмотрены FR-210; отдельная проверка полномочий целевого URL сохранена. Save только после commit, ошибки не являются success; свойства и публичные эффекты перечислены по поверхностям для form, wall и widget. На этапе дизайна нельзя утверждать, что они действительно работают.
- Все шесть выбранных настроек имеют назначенный reader; platform-label toggle должен скрывать название и сохранять provenance и badge. Legacy HTTP logo не блокирует Save несвязанного поля; новый HTTP получает объяснение, native pattern не обходит dirty validation. Rating sort, video-first и неутверждённые цены/лимиты исключены из production, а согласованный layout остаётся эталоном. В frozen prototype поле цвета представлено двумя синхронизированными control; общая обязанность реального эффекта для доступного control остаётся обязательной для реализации и проверки.
- Collect: предусмотрены отсутствие регистрации, отправка текста/фото, pending до owner moderation и появление approved на wall/widget. 201 единственный success; pending не обещает приватность photo URL. При 400/404/429/503 и network failure введённые поля и файл сохраняются, повтор возможен после завершения, двойной click во время отправки блокируется; неопределённый network outcome не гарантирует exactly-once.
- Независимо подтверждён **TESTABILITY-01** владельца `qcsd-testability`: текущий `submit-form.tsx` ставит `maxLength=80` на исходное имя, но `testimonial.ts` проверяет длину после trim и сохраняет исходную строку. Пробелы вокруг 80 букв допустимы сервером и недоступны обычному вводу. Это условие не подписывается повторно данным reviewer; необходимо его закрытие владельцем в общем синтезе.
- ADR-003 и FR-208 требуют две разные проверки: offline render тех же production components с frozen моделью на трёх размерах и отдельный интерактивный E2E обычных маршрутов. Эти будущие доказательства не заменяют друг друга; initial idle baseline не доказывает success/error/loading/dirty/dark состояния. Реализация и доказательства ещё не представлены.
