вызвана по `HAS_UI=true` (редактор, публичная форма, wall и widget). Вердикт

последующей проверки их автором этих условий. Это оценка замысла, не аудит готового
продукта и не подтверждение соответствия WCAG 2.2 AA.

## ACCESSIBILITY-01 — контраст текста и состояний

**HIGH, structural.** OpenSpec NFR-201 требует доступного текста для light/dark
и крайних HEX; `01_requirements.md` и `05_architecture.md` говорят об accessible
foreground отдельно от произвольного accent. Но текст на accent и accent как цвет
текста на нейтральном фоне — разные пары. Frozen `.cab-collection h1` и текущий
`/f/[slug]` используют accent как цвет заголовка на фоне карточки. Например,
`#FFFFFF` на белом фоне даёт 1:1: чёрный foreground, выбранный для кнопки с
белым accent-фоном, сам по себе не исправит заголовок. Аналогично нужно проверить
границы controls, ссылки и focus с окружающим цветом, в том числе в Shadow DOM.

Требуется зафиксировать в измеряемых проектных входах стратегию, применимую к
**каждой реальной паре** foreground/background, включая fallback/коррекцию для
accent-текста, и тестовый oracle для computed результата после compositing. На
реальных form, wall и widget сравнить в каждой теме чёрный, белый и близкие к
фону промежуточные допустимые HEX; обычный текст ≥4.5:1, крупный ≥3:1,
необходимые элементы управления и focus различимы ≥3:1 относительно соседнего
цвета. Проверка должна обнаруживать случай, в котором заголовок сливается с фоном,
даже если текст на акцентной кнопке имеет достаточный контраст. Исследовать реальные
CSS-токены и элементы после реализации; static pixel match не является этим oracle.

## ACCESSIBILITY-02 — имена, статусы и фокус в живых состояниях

**HIGH, structural.** NFR-201 требует labels, доступные ошибки/status и фокус при
успехе/ошибке; архитектура называет keyboard/focus, но не устанавливает oracle для
переходов. На существующем baseline у file input визуальный текст находится в
соседнем `span`, а не связанном label; список ошибок и заменяющий форму success
не имеют явной связи/фокусировки в показанной разметке. Это факты статического
чтения прежней формы, не вывод о будущей реализации. Frozen markup иначе связывает
file label, но offline fixture не доказывает живое поведение.

В дизайн и проверки добавить следующие наблюдаемые свойства для branding и collect:

- Idle: доступное имя и понятная связь подсказок для каждого input, включая file,
  color picker и HEX; видимый фокус и логичный Tab/Shift+Tab без ловушки.
- Sending/saving: объявляется занятое состояние, повторная отправка заблокирована,
  фокус не теряется непредсказуемо; после отказа сохранённый ввод доступен для повтора.
- Ошибка: содержательное сообщение связано с полем или сводкой, фокус направлен к
  ошибке/сводке, пользователь может исправить ввод и повторить; проверить как
  client validation, так и 400/429/503/network. При `noValidate` в ADR-001 нельзя
  рассчитывать на встроенное сообщение браузера как единственный доступный ответ.
- Success: только подтверждённый сервером успех виден и доступен для объявления;
  фокус переведён к видимому результату и обеспечено его доступное объявление в
  рамках NFR-201, с дальнейшей навигацией без ловушки.
- Legacy: клавиатурой сохранить тему при неизменённом HTTP logo; убедиться в
  отсутствии ложной ошибки и сохранении URL. После изменения на HTTP получить
  связанную с logo понятную ошибку, доступную с клавиатуры, без записи.

В обычных маршрутах проверить Tab/Shift+Tab/Enter/Space, имена/связи и переходы
через дерево доступности, а также вручную реальным screen reader. Проверка должна
падать при удалении связи или сообщения, а не только при наличии DOM узла.

## ACCESSIBILITY-03 — длинные значения и мобильный reflow

**WARNING, structural.** Архитектура предусматривает 360/390 frozen snapshot и
упоминает long strings в живом E2E, но не определяет вход и наблюдаемый результат.
Доступны heading до 120, URL до 2048, исходные имя/роль/отзыв и имя фото. Frozen
CSS имеет отдельный `overflow-wrap` для некоторых заголовков, но не явно для collect
h1; статический эталон с короткими literals не устанавливает reflow длинной строки.
Это не утверждение об обнаруженном runtime overflow.

Проверить обычные страницы на 360 и 390 CSS px и reflow до 320 CSS px с длинным
неразрывным heading, именем/ролью, именем фото, текстом ошибки и URL; содержимое,
контролы и фокус доступны и видимы без горизонтальной прокрутки основного документа.
Проверить также узкий host widget с длинным отзывом и provenance. Не усекать
пользовательский текст ради прохождения; нужен очевидный отрицательный oracle при
появлении обрезки либо недоступного за краем контрола.

## Предлагаемая проверка после реализации

Browser E2E на изолированных обычных routes должен наблюдать реальные computed
стили и accessibility tree в перечисленных состояниях и отрицательных случаях;
дополнить автоматизацию ручной keyboard/screen-reader проверкой. Проверить, что
мутация контраста, скрытие/разрыв ошибки и переполнение ломают соответствующие
oracles. Сначала автор меняет только нужные измеренные дизайн-входы, затем host
обновляет snapshot и отправляет этому независимому reviewer фактическую author
handoff для focused verification; текущая запись не закрывает эти условия. Отдельно
остаются реальный QE, визуальная приёмка и owner approval по проектному workflow.
