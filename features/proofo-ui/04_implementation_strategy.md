# Стратегия реализации после согласования

> Это срез публичной фазы. Последующее исследование разрешённого аккаунта описано в [07](07_authenticated_screen_map.md) и [08](08_authenticated_interaction_coverage.md); платные и заполненные состояния по-прежнему не подтверждены.

Сейчас готовы аудит и предложение разбиения. App-код и backend пока не меняются. Для макета на VPS добавлены read-only mount и отдельный статический Caddy-маршрут /__design/proofo/; контейнер Caddy пересоздан. [Предварительный scope](00_scope_assessment.md) и [карта экранов](03_screen_map.md) задают границы будущего плана.

## Порядок блоков

1. **Закрепить evidence и макет.** Сопоставить `preview/` с публичными снимками; зафиксировать версии desktop/mobile и явные отличия: исправление mobile overflow, бренд Proofwall, юридические/коммерческие тексты, неизвестные состояния. Согласование конкретного макета требуется AGENTS.md перед UI-кодом. Доступ в кабинет для этого не нужен.
2. **Формализовать публичную дельту.** Feature-adr/OpenSpec: отдельная оценка сложности, FR → requirement/scenario с SHA-256, reuse, применимые ADR/QCSD/архитектура, план и реальные K1/K2/checkpoints. Эти gates ещё не выполнены. Решения по URL стены, ratings и тарифным обещаниям принять до зависимого кода.
3. **Общие визуальные элементы + landing/auth.** Начать с ограниченной области публичных styles, типографики, header/footer, полей и карточек. Переиспользовать регистрирующую/входную логику и атрибуцию. Не менять глобальные tokens вслепую: они затрагивают кабинет, partner и формы.
4. **Help и legal.** Семь help-маршрутов через общий шаблон/данные; три legal-экрана через общий документный layout. Проверить работоспособный Proofwall embed, а утверждение юридических и коммерческих текстов сделать явной зависимостью публикации.
5. **Публичная стена.** Сохранить SSR и approved-query, безопасный рендер, noindex/JSON-LD; добавить измеренную композицию и masonry с читаемым fallback. Данные рейтингов — отдельная миграция/контракт, если включены в допущенный scope. Старые `/w/{slug}` ссылки сохранять; alias `/{slug}` требует решения о зарезервированных путях/canonical/коллизиях.
6. **Проверка и тестовая копия.** Проверки ниже, независимый cross-model QE, ссылка и инструкция владельцу, ручная приёмка. Production-поставка отдельно разрешается после приёмки того же артефакта. Работающее приложение сохраняется до UI approval; статический preview опубликован отдельно на том же VPS.
7. **Новая фаза после доступа.** Исследовать кабинет и actual flows; затем отдельные согласованные блоки OCR, управления отзывами, настроек и оплаты. Размер/порядок этих блоков уточняется по evidence, не по названиям событий JS.

## Где нужна серверная возможность

| Возможность | Reuse | Недостающая дельта / граница |
|---|---|---|
| Регистрация/login/forgot | Существующие API/session/slug | Визуальная смена сама по себе не требует нового auth backend; работоспособность на test-стенде ещё проверить |
| Help/legal | Статические маршруты и шаблоны | Новая серверная возможность не нужна, кроме корректной конфигурации собственного embed URL |
| Звёзды/среднее стены | Публикация approved и source proof | В текущем wall projection нет rating: nullable поле, валидация, происхождение оценки, агрегация только оценённых approved. Не выводить выдуманную оценку и не менять created_at на дату внешнего отзыва без источника |
| OCR screenshot import | Upload/storage, tenant, текущая модерация; CSV-паттерн preview→confirm | Отдельная extraction capability: распознавание → проверка/правка владельцем → подтверждённая запись; состояния ошибки/повтора, лимиты и стоимость, идемпотентность, исходный screenshot и provenance. Выбор sync/job/provider только после требований. Нельзя выдавать STT или сохранение screenshot за OCR; новое ADR должно согласовать это с текущей границей AI, запрещающей переписывание отзывов |
| Start/Pro/кампании/много стен | Существующие billing, tariff, webhook | Три marketing-карточки не доказывают три реализованных тарифа. Entitlements, лимиты/кампании и paid UX требуют отдельных требований и backend; Proofo runtime неизвестен |
| Редакторы/аналитика/настройки | Есть чтение branding/разрозненные events | Потребность и контракты unknown. Не создавать CRUD или dashboard по догадке |

## Минимальная визуальная и E2E-приёмка

- **Visual:** одинаковые фиксированные данные, загруженные шрифты и viewport; desktop 1440, mobile 390, дополнительный узкий 360 px на overflow. Full-page сравнения для landing/auth/help/wall; legal и platform-варианты после получения baseline. Проверяются геометрия, переносы, порядок, видимость CTA и длинные тексты. Допуски diff согласуются с макетом; одна общая процентная метрика не скрывает сломанный блок. Принятые отличия регистрируются явно.
- **Public E2E:** hash-навигация/CTA, семь help URL, три legal URL, доступные подписи полей и клавиатура, регистрация/slug/ошибки, login/next, forgot/status. Loading/disabled/validation/network/429 воспроизводятся контролируемыми фикстурами; контрактные проверки с test-API отдельно от mock UI.
- **Wall regression:** published/empty/404, отзывы без оценки, агрегат только по оценённым, длинные данные, источники/badge, SSR без JS, JSON-LD/noindex, XSS текст остаётся видимым и не исполняется, tenant isolation. Добавление client masonry не должно делать контент зависимым от гидратации.
- **Существующий core CJM:** регистрация → текстовый отзыв → модерация → стена → виджет на втором origin. Проверить серверный badge/тариф; если затронут billing — отдельная TEST-проверка идемпотентности и отказа/повтора. Не менять платёжный runtime ради визуального аудита.
- **Инженерные gates:** применимые lint/typecheck/build и существующие тесты изменённых областей; widget budget/Shadow DOM при его изменении. Отчёт содержит SHA артефакта, браузер/viewport, screenshots/traces, passed/failed/skipped и ограничения среды. Наличие теста в репозитории не равно выполненному тесту.

Главные риски: разрастание публичного scope в недоступный кабинет, CSS-регрессии существующих flows, выдуманные рейтинги/тарифы, подмена OCR ручным импортом, потеря безопасности SSR/widget и исчезновение временных evidence. Разбиение по независимым публичным семействам с отдельной backend-дельтой уменьшает область каждой приёмки. Полное UI/UX-соответствие Proofo до исследования закрытой части не заявляется.

Фактическая публикация макета: HTTPS /__design/proofo/, отдельный read-only mount только preview/, X-Robots-Tag noindex/nofollow. Это изменение Caddy-конфигурации и пересоздание Caddy, не поставка нового приложения, не перенос данных и не переключение DNS.
