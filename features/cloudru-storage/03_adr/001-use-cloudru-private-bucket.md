# ADR-001: Cloud.ru через существующие S3-клиенты

## Status
proposed — обратимо до записи новых объектов; после начала записи переключение назад требует отдельной оценки доступности данных. Пересмотреть при изменении политик бакета/формата ключей.

## Контекст
Локальное MinIO заменяется существующим частным бакетом Cloud.ru `proofwall`. Web пишет медиа и читает фото; worker подписывает GET. Исторические документы требуют MinIO, но текущая постановка разрешает замену backend без изменения продуктового контракта. Связь: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6.

## Decision Drivers и варианты
Главные факторы: существующий bucket владельца (high), сохранность контрактов (high), минимум новой логики (medium). Вариант 1 — параметризовать нынешние клиенты: сохраняет API и соответствует выбранному Cloud.ru; минус — облачные права и совместимость требуют отдельной проверки. Вариант 2 — оставить обязательное MinIO: знакомый локальный backend и контроль данных; минус — обслуживание на VPS и несоответствие выбранному владельцем storage. Отдельный общий SDK-пакет не нужен для двух конфигурационных мест.

## Решение
Параметризовать существующие клиенты; в Cloud.ru окружении `S3_ENDPOINT=https://s3.cloud.ru`, `S3_REGION=ru-central-1`, `S3_FORCE_PATH_STYLE=false`, оба bucket = `proofwall`. Для обоих клиентов установить requestChecksumCalculation и responseChecksumValidation в WHEN_REQUIRED. WorkerConfig.s3ForcePathStyle опционален; отсутствие нового поля сохраняет forcePathStyle=true старых вызовов. MinIO только в опциональном профиле. Данные, object keys, exports, API и TTL сохраняются.

Общий bucket остаётся частным: публичность фото обеспечивает существующий маршрут с regex и sniffImage; видео не становятся доступны через него. Исправить устаревший комментарий о необходимости разных bucket, не ослаблять маршрут. Ключи вводит владелец только в ignored `/home/proofwall/.env` mode 600. Новый probe не требуется.

## Последствия
Плюс: единый выбранный backend без нового слоя и переноса данных. Минус: внешний сетевой сервис и общая bucket policy; смягчение — HTTPS, private bucket, прежний фильтр фото и targeted тесты. При недоступности сохраняются StorageError/503 и существующая обработка worker. Производительность и реальные права пока не измерены. Follow-up ADR пока не нужен; владелец/coder пересматривают решение через месяц после приёмки.

## Confirmation
Method: локальные HTTP capture/presign тесты, regression, Compose wiring; затем независимое ревью и медиа-CJM с пользовательскими ключами. Monitoring: существующие storage error события и результат медиа-CJM. Success metric: все локальные assertions проходят, внешний запрос подписан нужным регионом/host, фото-route отвергает видео; runtime остаётся pending до реального прогона. Owner: coder и независимый reviewer; runtime — владелец стенда.

Load-bearing property: корректные регион/host/checksum проверяются `apps/web/tests/storage-cloudru.test.ts` и `services/worker/tests/storage-cloudru.test.ts`; прежние ключи/фото-границы — первым файлом и regression `apps/web/tests/photo.test.ts`; worker TTL и старый config — вторым файлом. HTTP capture должен наблюдать сериализованный запрос SDK, а не только переданные конструктору options. При возврате forcePathStyle=true или удалении WHEN_REQUIRED соответствующий тест должен упасть. Облако недоступно: API возвращает прежнюю ошибку, mock-тест не становится runtime-доказательством.
