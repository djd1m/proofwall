# Proofwall — инструкции для работы

Самостоятельный проект: `/home/proofwall`, GitHub `djd1m/proofwall`, ветка `main`.
Методика перенесена из Clipmkr 11.11.2026; продуктовые требования Clipmkr не перенесены.
Эти правила применяются к дальнейшей работе после подготовки репозитория.

## Перед задачей

1. Прочитать `CLAUDE.md`, `docs/development/workflow.md`, применимые `.claude/rules/`,
   `docs/acceptance/core-cjm.md` и относящиеся к задаче требования/ADR.
2. Назвать объём, роли и фактические модели, инструменты, проверки и результат.
   Не запускать команду агентов ради простой операции с файлами; для продуктовых
   изменений применять независимое ревью по `docs/review-policy.md`.
3. Выполнить `npm run dz -- recall "<тема>" --project /home/proofwall --limit 3`;
   прочитать результат. Пустой ответ или ошибка не означают применение знания.
4. Новые фичи вести по локальному `.agents/skills/feature-adr/SKILL.md`:
   сложность → требования → reuse → применимые ADR/QCSD/архитектура → план →
   настоящие K1/K2/checkpoints → код → тесты/QE → независимое ревью → anti-drift.
   Не выдумывать успешные gates, receipts, разрешения владельца или результаты проверок.

## Источники и процесс

- Нормативная дельта нового поведения — `openspec/changes/<slug>/specs/`.
  В `features/<slug>/01_requirements.md` указывать FR → requirement/scenario,
  путь и SHA-256 дельты. Обновлять обе привязки согласованно.
- Исторический SPARC-контекст остаётся в `docs/Specification.md`, `Architecture.md`,
  `Pseudocode.md`, `ADR.md`, `Refinement.md`, `Completion.md`. Архив не доказывает
  текущее поведение; при конфликте сначала установить применимую ревизию.
- Сначала reuse действующих блоков Proofwall, затем поддерживаемых OSS.
  Сохранять npm workspaces и существующие границы сервисов.
- Новые инструкции и отчёты писать по-русски. Небольшие проверенные коммиты;
  репозиторий назначения — только `origin` (`djd1m/proofwall`). GitLab/GitVerse,
  домены, платёжные настройки и production Clipmkr к этому проекту не относятся.
- Закреплённые версии: harness-cli 0.8.58, skills-feature-adr 1.5.25,
  OpenSpec 1.15.0. Использовать `npm run dz -- ...` / `npm run openspec -- ...`,
  а не случайный глобальный CLI. `npm run process:install` восстанавливает навыки.
- Проектный Node.js 22.23.4 закреплён devDependency `node`: npm scripts используют
  локальный бинарник автоматически. Системный Node.js этим не меняется.

## UI, проверка и поставка

- Перед реализацией UI показать конкретный макет владельцу и согласовать его.
- Цикл: согласованный макет/план → тестовая копия → E2E UI/UX → ссылка и инструкция
  владельцу → ручная приёмка → отдельно разрешённая production-поставка того же артефакта.
  Домен/стенд Proofwall на этом VPS ещё не выбран. Не подставлять адрес Clipmkr.
- Перед Compose проверить порты и окружение. Не перезаписывать существующие данные,
  не переключать DNS и не применять миграции к чужим/production-БД без явного поручения.
- Для кода выполнить применимые тесты, lint/typecheck/build и интеграцию/E2E по риску.
  Для переноса документов проверять комплектность, пути и инструменты; не выдавать
  эту проверку за приёмку приложения. Skipped/inconclusive описывать явно.
- Перед завершением записать FR → spec → код → проверку и ограничения.
  Не объявлять авторскую проверку независимым ревью.

## Обучение

Принятое замечание владельца: recall → подтверждённое наблюдение и доказательства →
`npm run dz -- teach "<урок>" --type lesson-learned --project /home/proofwall --no-mirror`
→ проверить ответ → повторный recall → применить урок. Store `.dz/` локальный и не коммитится.
Не переносить память Clipmkr как будто это подтверждённые уроки Proofwall.
Секреты, `.env`, дампы, приватное медиа и подписанные URL в Git не помещать.
